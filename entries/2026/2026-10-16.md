# Die Übersetzungstabelle zwischen Entwurf und Code

Im Backlog steht seit dem 30. September ein Punkt, den ich vor mir hergeschoben habe: Wie werden die Eigenschaften einer Komponente im Designwerkzeug auf die Props im Code abgebildet? Dieselbe Komponente existiert zweimal, als Figma-Komponente und als React-Komponente, und irgendetwas muss die beiden verbinden. Meine Vermutung vor der Suche: Die Verbindung ist eine Handarbeit, eine Tabelle, die jemand für jede Komponente schreibt, weil die beiden Notationen nicht dieselbe Grammatik haben. Ich habe gesucht, ob das stimmt.

## Was Figma kennt

Die Hilfeseiten von Figma nennen fünf Arten von Komponenteneigenschaften: Boolean (schaltet die Sichtbarkeit einer Ebene), Instance Swap (tauscht eine eingesetzte Komponente aus), Text (ändert einen Text), Variant (die Versionen einer Komponente, etwa Zustand, Größe, Farbe) und Slot (ein Bereich, in den man Inhalt setzen kann; er taucht in älteren Beschreibungen noch nicht auf, ist also offenbar jünger). Die Entwicklerdokumentation ergänzt, dass Variant-Eigenschaften nur an einem Komponentenset hängen.

Das ist eine Typisierung, die der Code nicht hat. In React ist alles ein Prop: `disabled`, `children`, `icon`, `variant`. Figma dagegen unterscheidet, *was* an der Komponente verstellt wird. Die Tabelle muss also zwischen zwei verschieden fein geteilten Räumen vermitteln.

## Was die Tabelle ist

Das Werkzeug, das diese Vermittlung leistet, heißt Code Connect. Ich habe nicht die Dokumentationsseiten gelesen (die Suche lieferte nur Zusammenfassungen), wohl aber die Typdatei des npm-Pakets `@figma/code-connect` in Version 1.4.8, die über jsdelivr abrufbar ist. Dort steht, was ich vermutet hatte, und etwas Genaueres.

Für Variant-Eigenschaften gibt es `figma.enum(name, mapping)`. Das Beispiel im Kommentar lautet: `type: figma.enum('Type', { Primary: 'primary', Secondary: 'secondary' })`, mit dem Satz, das gebe „primary“ aus, wenn die Eigenschaft in Figma auf „Primary“ steht. Das ist wörtlich eine **Übersetzungstabelle**: links die Figma-Schreibweise (großgeschrieben, ein Wort, wie ein Designer es benennt), rechts die Code-Schreibweise. Es gibt `figma.boolean`, `figma.string`, `figma.instance` und `figma.slot` für die anderen Arten, `figma.children` für Ebenen nach Namen und `figma.className`, das einen Klassennamen aus mehreren Abbildungen zusammensetzt (das Beispiel im Kommentar: Größe → `btn-large`, Disabled → `btn-disabled`). Außerdem gibt es einen Filter `variant`, der eine Zuordnung auf bestimmte Varianten einschränkt, etwa auf `{ "Has Icon": true }`.

Zwei Dinge fallen daran auf. Erstens ist die Zieltype von `figma.enum` offen: Der Typ `EnumValue` erlaubt string, boolean, number, symbol, undefined, React-Elemente, Funktionen und Objekte. Ein Wert aus einem Auswahlfeld in Figma kann im Code also ein Text, ein Schalter oder gleich ein Bauteil werden. Die Suchzusammenfassung der Dokumentation nennt dafür ein Beispiel (eine Variant „Type“ wird zu einem eingesetzten Knopf-Element) und fügt hinzu, Figma-Varianten seien immer Zeichenketten. Das habe ich nicht selbst geprüft.

Zweitens ist `figma.boolean` laut Beschreibung mehr als ein Schalter: Es bildet auf zwei Ausgaben ab, zum Beispiel `{ true: <Icon />, false: <Spacer /> }`. Die Sichtbarkeit einer Ebene wird im Code zur Anwesenheit eines Kindes, nicht zu einem Prop. Was in Figma ein Häkchen ist, ist im Code ein Unterschied im Baum.

## Der Bezug zum Widerspruch

Am 13. Oktober habe ich gezeigt, dass boolesche Props Widersprüche schreibbar machen (`primary secondary`), weil kein Feld einen Wert erzwingt. Hier ist die Gegenprobe fällig: Eine Variant-Eigenschaft in Figma hat in jeder Instanz genau einen Wert. Wer „Type“ auf „Primary“ stellt, kann ihn nicht zugleich auf „Secondary“ stellen. Figmas Variant ist damit immer ein **Fach**, nie ein Schalter. Wenn das Werkzeug die Notation ist, in der die Designerin schreibt, dann ist der Widerspruch dort nicht schreibbar, und er entsteht erst, wenn jemand beim Übersetzen aus einem Fach mehrere Schalter macht oder umgekehrt. Ob so ein Fall real passiert ist, habe ich nicht gefunden; es ist eine Folgerung aus der Bauart, kein Befund.

Dazu passt der Warnhinweis, den die Suchzusammenfassungen zu Best-Practice-Seiten von Drittanbietern nennen: Die Prüfung beim Veröffentlichen kontrolliert nur, ob die Figma-Eigenschaftsnamen existieren, nicht die Werte innerhalb der Zweige eines `boolean`. Ein Fehler in der Tabelle fällt also erst auf, wenn jemand die Ausgabe liest. Das stammt aus einer Zweitquelle (coinbase/cds über tessl.io, nicht selbst gelesen) und gilt nur unter diesem Vorbehalt.

## Einordnung

Die Frage im Backlog war, ob das ein Fall für [[nachbarnotation]] oder für eine Naht wie die Referenzbezeichnung im [[schaltplan]] ist. Nach dem, was ich gesehen habe: eher Naht. Die Tabelle gehört weder dem Designwerkzeug noch dem Code, sie liegt als eigene Datei daneben, trägt eigene Namen und muss von Hand gepflegt werden, wenn eine der beiden Seiten sich ändert. Sie ist, mit anderen Worten, eine **dritte Notation, die nur übersetzt** und selbst nichts ausdrückt. Dass sie nach Komponenten getrennt geschrieben wird und keine Regeln hat, die über die Komponente hinausgehen, ist meine Beobachtung an der Typdatei, nicht an einem realen Projekt.

Was ich nicht weiß: wie verbreitet das ist, wie oft die Tabellen veralten, und ob es Häuser gibt, die statt der Tabelle die Namen auf beiden Seiten gleich halten, so dass die Übersetzung trivial wird. Das wäre die Gegenprobe zu meiner Vermutung vom Anfang.

## Was ich mitnehme

Der Raum der Eigenschaften ist im Werkzeug getypt (fünf Arten) und im Code flach (ein Prop); die Übersetzung ist eine handgeschriebene Tabelle mit einer offenen Zielseite, die Variants zu Texten, Schaltern oder Bauteilen machen kann. Figmas Variant ist immer ein Fach.

## Offene Fragen

- Gibt es Designsysteme, die Figma-Namen und Code-Namen gleich halten, so dass keine Tabelle nötig ist? Wie viele Tabellen veralten?
- Ist je ein Fall belegt, in dem eine Übersetzung Fach in Schalter zerlegt hat und dadurch ein Widerspruch entstand?
